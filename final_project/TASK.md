# Фінальний проект

Це фінальний проєкт для цього курсу. Розглядайте наведений далі опис як рекомендацію. Він дає змогу використовувати різні технології, а це означає, що реалізація може відрізнятися. Він навмисно не містить усіх деталей, щоб ви могли придумати своє унікальне рішення. Будь ласка, використовуйте всі знання та навички, набуті в попередніх модулях, і запропонуйте власний варіант реалізації.

Після завершення цього модуля ви зможете:
- створити унікальне рішення для автоматизації розгортання застосунку в хмарі 
- налаштувати моніторинг розгорнутого застосунку
- підготувати діаграму архітектури реалізованого рішення

Створіть CI/CD-рішення для застосунку на ваш вибір або готове рішення — Java-проєкту spring-petclinic — та розгорніть контейнерний застосунок у хмарі.

# Компоненти:
- діаграма архітектури 
- автоматизація інфраструктури 
- CI/CD-рішення
- моніторинг

- Інструмент автоматизації інфраструктури: Terraform
- Віддалене сховище даних для Terraform: Amazon S3, Azure Blob Storage, 
- Google Cloud Storage або керований GitLab стан Terraform
- Інструмент управління конфігурацією: Ansible

- Артефакти: Docker-образи
- Зберігання артефактів: Nexus, GitLab Container Registry, Docker Hub або хмарний сервіс (Elastic Container Registry, Google Container Registry або Azure Container Registry)
- Постійна база даних для застосунків: Amazon RDS для MySQL, Azure Database для MySQL або Cloud SQL в GCP
- Скрипти: Python та/або Bash

# Terraform

Ваш пайплайн з Terraform повинен охоплювати такі завдання:
- форматування конфігурації
- перевірка та сканування конфігурації (необов’язково), планування
- розгортання ресурсів (ручна робота)
- знищення ресурсів (ручна робота)

Використовуйте Terraform для створення таких ресурсів у хмарі:
- Віртуальна машина з усіма необхідними мережевими ресурсами та балансувальником навантаження. Ця віртуальна машина буде для розміщення застосунку.
- Постійна база даних для застосунку.
- (Необов’язково) Додаткова віртуальна машина з усіма потрібними мережевими ресурсами для запуску додаткового програмного забезпечення, наприклад, GitLab runners, Nexus (якщо застосовують).

# Рішення CI/CD

Рішення для безперервної інтеграції та безперервної доставки (CI/CD) для Java-застосунку spring-petclinic або вашого застосунку.
Репозиторій з вихідним кодом застосунку spring-petclinic або вашого застосунку повинен додатково містити конфігураційні файли для Maven або Gradle та Docker-файл.

Пайплайн для запиту на злиття (MR) або на витягування (PR) повинен охоплювати:
- статичний аналіз коду
- тести
- збірку
- створення артефакту (його можна позначити коротким хешем 
фіксації) переміщення артефакту до сховища артефактів

Пайплайн для основної гілки повинен охоплювати:
- створення Git-тегу в сховищі з використанням підходу Semantic Versioning (з кожним 
комітом збільшується мінорна версія). Тут можна застосувати python-скрипт із semver — PyPI
- створення артефакту з Git-тегом, що представляє версію
- переміщення артефакту до сховища артефактів
- завдання ручного розгортання, яке підключається до віртуальної машини, перевіряє наявність попередньої версії програми та видаляє її
- отримує образ зі сховища артефактів
- запускає застосунок
- друкує посилання на застосунок
